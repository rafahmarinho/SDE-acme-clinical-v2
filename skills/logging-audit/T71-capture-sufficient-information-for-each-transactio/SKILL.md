# T71: Capture sufficient information for each transaction in audit logs

**Category:** CODE_FIX
**SD Elements:** [T71](https://sde-ent-echo.sdelab.net/bunits/afrika-sc-labs/acme-clinical-v2/acme-clinical-v2/tasks/phase/development/32-T71/)
**Priority:** 3/10 · **Phase:** development

**Spec Context:**
> "acompanhar manutenção. Reconhecer um alarme não encerra uma condição que ainda está"
> (EN: track maintenance. Acknowledging an alarm does not end a condition that is still)
> Source: specs/PRD.md, line 35

> "escolher cenários, avançar a simulação, consultar eventos e reiniciar os dados."
> (EN: choose scenarios, advance the simulation, view events and reset the data.)
> Source: specs/PRD.md, line 43

**What the spec implies (naive approach):**
A simple `events(id, type, message, created_at)` table filled with free-text messages. It lacks who acted, from where, the outcome, and mixes trusted server data with user-supplied text, so investigations of who acknowledged an alarm are impossible.

**Secure Implementation Pattern:**
```sql
-- supabase/migrations/0001_schema.sql
create table public.audit_events (
  id            bigint generated always as identity primary key,
  occurred_at   timestamptz not null default clock_timestamp(),   -- UTC, microsecond precision
  actor_id      uuid references auth.users(id),
  actor_role    text not null,                                     -- nurse|physician|biomed|admin|system
  source_ip     inet,
  action        text not null check (action ~ '^[a-z_]+\.[a-z_]+$'),
  target_type   text not null,
  target_id     text,
  outcome       text not null check (outcome in ('success','failure')),
  error_code    text,
  details       jsonb not null default '{}' check (pg_column_size(details) < 4096),
  user_supplied jsonb not null default '{}' check (pg_column_size(user_supplied) < 2048)  -- untrusted, kept separate
);
```
```python
# backend/app/services/audit.py (or core/logging.py)
async def audit(db, request, user, action, target_type, target_id, outcome="success",
                error_code=None, details=None, user_supplied=None):
    await write_audit(db, {
        "actor_id": user.id if user else None, "actor_role": user.role if user else "system",
        "source_ip": request.headers.get("x-real-ip") or (request.client.host if request.client else None),
        "action": action, "target_type": target_type, "target_id": str(target_id),
        "outcome": outcome, "error_code": error_code,
        "details": details or {}, "user_supplied": {k: str(v)[:200] for k, v in (user_supplied or {}).items()},
    }, critical=(action == "alarm.acknowledge"))
```

**Implementation Guidance:**
- Create `audit_events` in `supabase/migrations/0001_schema.sql`; timestamps are generated by the database clock (`clock_timestamp()`, UTC `timestamptz`) so all components share one time reference.
- Call `audit()` from each router: `alarms` (acknowledge — note an acknowledgement does not close the condition; log both `alarm.raised`, `alarm.acknowledge`, `alarm.cleared`), `observations`, `thresholds`, `monitors` (bind/unbind), `maintenance`, `staff`, `simulation` (scenario, advance, reset), `reports`, `files`.
- Keep server-derived fields (`details`) separate from untrusted input (`user_supplied`), cap sizes with CHECK constraints and truncation.
- Record failures too (`outcome='failure'`, `error_code`), including authorization denials.
- The "consultar eventos" screen reads this table (read-only; see T350). Do not store PHI (T46).
- Reference: SD Elements guidance for T71.

**Success Criteria:**
- [ ] `audit_events` migration exists with the columns and constraints above.
