# T86: Test session ID uniqueness and rotation after authentication

**Category:** CODE_FIX
**SD Elements:** [T86](https://sde-ent-echo.sdelab.net/bunits/afrika-sc-labs/acme-clinical-v2/acme-clinical-v2/tasks/phase/testing/32-T86/)
**Priority:** 9/10 · **Phase:** testing

**Spec Context:**
> "Use versões atuais e estáveis das tecnologias e Supabase para PostgreSQL, login por e-mail e"
> (EN: Use current, stable versions of the technologies and Supabase for PostgreSQL, email and [password] login)
> Source: specs/PRD.md, line 5

**What the spec implies (naive approach):**
The team would rely on Supabase Auth and assume session handling is correct. Session identifiers are generated by Supabase (the `session_id` claim, refresh tokens) and by any custom layer ACME adds (`app_sessions`, optional refresh cookie). A custom layer that reuses a pre-login value, keys sessions on `user_id`, or upserts the same row on every login would silently break rotation and enable session fixation.

**Secure Implementation Pattern:**
```python
# backend/tests/test_session_rotation.py
async def test_each_login_creates_new_session(supabase_login, api):
    ids, refresh_tokens = set(), set()
    for _ in range(20):
        s = await supabase_login("demo.physician@acme-clinical.test")
        await api.post("/auth/session", headers=s.auth_header)
        ids.add(s.session_id); refresh_tokens.add(s.refresh_token)
    assert len(ids) == 20 and len(refresh_tokens) == 20          # unique per login
    assert all(uuid.UUID(i).version == 4 for i in ids)           # random UUIDs, not sequential

async def test_app_session_not_keyed_on_user(api, supabase_login, db):
    a = await supabase_login("demo.nurse@acme-clinical.test"); await api.post("/auth/session", headers=a.auth_header)
    b = await supabase_login("demo.nurse@acme-clinical.test"); await api.post("/auth/session", headers=b.auth_header)
    assert a.session_id != b.session_id
    assert await db.fetchval("select count(*) from app_sessions where session_id in ($1,$2)", a.session_id, b.session_id) == 2

async def test_refresh_token_rotates_and_reuse_is_detected(supabase_login):
    s = await supabase_login("demo.nurse@acme-clinical.test")
    r1 = await supabase_refresh(s.refresh_token); assert r1.status_code == 200
    assert r1.json()["refresh_token"] != s.refresh_token
    await asyncio.sleep(REUSE_INTERVAL + 1)
    assert (await supabase_refresh(s.refresh_token)).status_code in (400, 401)   # old token rejected

async def test_client_supplied_session_id_ignored(api, nurse):
    r = await api.post("/auth/session", headers=nurse.auth_header, json={"session_id": str(uuid.uuid4())})
    assert r.json()["session_id"] == nurse.session_id
```

**Implementation Guidance:**
- Place tests in `backend/tests/test_session_rotation.py`, running against a local Supabase stack with the seeded demo users.
- Randomness: session identifiers must come from Supabase Auth or `uuid.uuid4()` / `secrets.token_urlsafe(32)` in Python; grep the backend for `random.` used in security contexts and fail review if found.
- Rotation after authentication: before login the SPA holds no session; after login a new `session_id` must exist. If the optional FastAPI refresh cookie (T23) is implemented, assert that the cookie value differs before and after login and after every refresh.
- Confirm Supabase Auth settings: refresh token rotation enabled and reuse interval small (default 10 seconds); document the values in the README.
- `POST /auth/session` must derive `session_id` only from the verified JWT, never from the request body.
- Reference: SD Elements guidance for T86.

**Success Criteria:**
- [ ] Every login yields a unique, random `session_id` and refresh token.
- [ ] Refresh rotates the refresh token; reuse after the reuse interval fails.
- [ ] Client-supplied session identifiers are ignored.
- [ ] Tests pass in CI.
